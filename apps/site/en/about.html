About GymYar

GymYar is a fork of openGym, rebuilt so that two people — a coach and a client — can work on the same training without one of them silently overwriting the other.

What openGym was

openGym is a self-hosted gym and body-weight tracker by Duarte Santos, and it is very good at what it set out to do: log your workouts and your weight, on your own server, with no subscription and no account on someone else's machine. Guided sessions, 1,324 exercises with animations, a muscle map, progression that follows an actual rule, 12 languages. It was built by someone standing in a gym with the thing in their hand, and it shows.

Everything in GymYar's features list that concerns tracking came from there. None of it was rewritten for the sake of rewriting it.

The one thing that had to change

openGym stored a user's entire account as a single JSON document and synced it with a whole-state PUT — last write wins. For one person on their own server that is an elegant design: no schema to migrate, no merge logic, nothing to get wrong.

It is fatal for coaching. If a coach edits a programme while their client is mid-session, one of those two edits is destroyed and nobody is told. And a server that never parses what it stores can never answer a question about it — so "which of my clients has stalled?" is not a query, it is a thing that cannot be asked.

So GymYar stores rows. Every write bumps a per-user counter and records what changed at that value; a client remembers the last counter it saw and asks for whatever came after it. The app still holds the whole state in memory — that part was never the problem, and it is what keeps the app working with no signal in a basement gym — but the wire format and the database underneath are relational.

One mapper sits between the two worlds, imported by both the client and the server, so there is one of it rather than two that drift apart.

The rule that makes coaching safe

A coach never writes a client's rows. A proposed programme lands in its own table and becomes real only when the client accepts it — at which point it is written as the client's own row, through the ordinary sync path. There is only ever one writer per row, so there is nothing to merge, and a client's own edit cannot be erased by a coach's sync.

Scopes are the other half of it. Sharing a programme does not share what you weigh. Every coach-side read is checked against the scope that client granted, section by section.

What the AI layer is, and is not

The domain owns every number. Sets, reps, loads, progression policies and exercise selection are computed against the real library and the same progression rules the app already runs on. A language model is asked to do exactly two things: turn free text into a structured brief, and write the note explaining a change. Both have a deterministic implementation underneath them.

Which model does that is configuration — a hosted provider, or one on your own hardware as the failover underneath it, which is what an outage, a lapsed key and a blocked route all look like from here. With no key set at all, GymYar builds the same plans, finds the same stalls and parses the same logs; it phrases things from a template instead of writing prose, in whichever language the person is using, and the app says so plainly.

That is what makes it safe to expose. Nothing can invent a lift that is not in the library, or put 140 kg on a beginner's bar.

Three products, one codebase

The web app is the whole thing: accounts, sync, coaching, subscriptions. The native builds are a different product on purpose — an offline single-user tracker with no accounts, no backend and nothing to buy. Training data lives in a file on the phone, and the network layer throws if anything tries to reach a server, so the privacy declaration those builds ship with is enforced rather than promised.

Principles

  • Your data is yours. Local-first, one-file backups, no lock-in — leaving GymYar must always be one export away.
  • A client is never the product. Training is free and ungated. The only thing a subscription can ever gate is a coach taking on new work.
  • No telemetry, ever. If a feature needs analytics to justify itself, it does not ship.
  • The model never has the last word. Anything it produces is a draft that a person confirms, and there is a deterministic path underneath it that works with no model at all.
  • Open source that stays open. AGPL-3.0, so every fork and every hosted version owes its code back to everyone — this one included.
